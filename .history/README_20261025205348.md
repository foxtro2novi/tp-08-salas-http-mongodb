## 3. Configuración en MongoDB Atlas
1. Creé mi cuenta en Atlas y levanté un clúster gratuito Free (M0) en la región de San Pablo (sa-east-1).
2. En Database Access, creé un usuario para la base de datos con permisos de lectura y escritura en todas las bases (readWriteAnyDatabase).
3. En Network Access, agregué mi dirección IP actual a la lista blanca para poder conectarme desde mi máquina.
4. En Connect -> Drivers, elegí Node.js y copié la cadena de conexión con formato mongodb+srv://...
5. Le agregué al final de la ruta el nombre de la base de datos obligatorio para este TP: reservas_salas_u7.

Las credenciales reales las configuré en mi archivo local .env para que queden privadas y no queden expuestas en el código.

## 4. Instalación y comandos de ejecución

### 4.1. Instalación de dependencias
Al clonar el proyecto, se instalan los paquetes con:
npm install

### 4.2. Variables de entorno
Para configurar el entorno se debe copiar la plantilla de ejemplo:
cp .env.example .env

Contenido de la plantilla pública .env.example (sin contraseñas reales):
PORT=3000
NODE_ENV=development
MONGODB_URI=mongodb+srv://USUARIO:CLAVE@HOST/reservas_salas_u7?retryWrites=true&w=majority

En el archivo local .env se completan las credenciales reales de conexión. Este archivo está excluido del repositorio mediante .gitignore para no subir información sensible a GitHub.

### 4.3. Diagnóstico de DNS y resolutores
Al probar la conexión inicial con mongodb+srv://, Node.js tiraba errores de DNS (querySrv ENOTFOUND / ECONNREFUSED). Para solucionarlo sin tener que tocar la configuración de red de la computadora, apliqué el ajuste visto en clase dentro de src/config/base-datos.js, configurando los DNS públicos de Google y Cloudflare:
const dns = require("node:dns");
dns.setServers(["8.8.8.8", "1.1.1.1"]);

### 4.4. Scripts del laboratorio de consola
Para probar la base de datos de forma aislada se crearon tres programas en la carpeta scripts:

Comprobar la conexión con Atlas:
node --env-file=.env scripts/comprobar-conexion.js

Crear una reserva de prueba válida:
node --env-file=.env scripts/crear-reserva.js

Listar las reservas guardadas:
node --env-file=.env scripts/listar-reservas.js

### 4.5. Control de calidad y servidor web
Para formatear los archivos y chequear que no haya errores de sintaxis:
npm run format
npm run check

Para levantar el servidor web Express previo:
npm start

La web sigue funcionando en memoria y se puede abrir en:
http://localhost:3000/reservas

### Conceptos aplicados:
- Schema (esquema): Definido en src/modelos/reserva.js. Es el contrato donde declaramos qué campos componen una reserva, qué tipos de datos se permiten y qué validaciones deben pasar antes de guardarse.
- Model (modelo): Reserva es el modelo que creamos a través de Mongoose. Nos da los métodos necesarios para operar contra la base de datos, como create para insertar o find para consultar.
- Colección: El lugar físico dentro de MongoDB Atlas donde se almacenan los documentos BSON. La definimos explícitamente con el nombre reservas.

## 6. Campos del dominio y reglas de validación

- estudiante: Tipo String. Obligatorio y con trim para limpiar espacios en blanco en los extremos.
- email: Tipo String. Obligatorio, con trim y comprobación por expresión regular para exigir la presencia de @ (match: /@/).
- sala: Tipo String. Obligatorio y restringido por enum a tres opciones: "Sala Norte", "Sala Sur" o "Sala Multimedia".
- fecha: Tipo String. Obligatoria y validada para que no quede vacía después de aplicar trim.
- turno: Tipo String. Obligatorio y restringido por enum a: "Mañana", "Tarde" o "Noche".
- personas: Tipo Number. Obligatorio, validado como entero con Number.isInteger y en un rango de 1 a 6 (min: 1, max: 6).

Límites de esta entrega: Todavía no comprobamos si el correo existe realmente, ni controlamos solapamientos de turnos en una misma sala, reservas repetidas o si la fecha ingresada pertenece al pasado.

## 7. Evidencia de persistencia entre procesos

Para demostrar que los datos sobreviven al cierre de Node.js y quedan guardados en la nube, hice la siguiente prueba en la consola:

1. Ejecuté el listador con la base limpia (node --env-file=.env scripts/listar-reservas.js) y me devolvió: Total de reservas: 0.
2. Ejecuté el creador (node --env-file=.env scripts/crear-reserva.js) y guardó una reserva devolviendo su identificador único: _id: 6ade867824b013c1d9a3424b.
3. El script terminó y la terminal volvió al prompt normal, cerrando el proceso de Node.js por completo.
4. Abrí un proceso nuevo ejecutando otra vez el listador (node --env-file=.env scripts/listar-reservas.js). Recuperó la reserva con ese mismo _id (6ade867824b013c1d9a3424b) y el contador subió a 1.
5. Volví a consultar con el listador y la cantidad se mantuvo en 1 sin duplicar datos.
6. Entré a MongoDB Atlas en la sección Data Explorer y comprobé que el documento con el id 6ade867824b013c1d9a3424b quedó guardado en la colección reservas dentro de reservas_salas_u7.

Esto demuestra que la persistencia es real y no depende de la memoria RAM del proceso.
