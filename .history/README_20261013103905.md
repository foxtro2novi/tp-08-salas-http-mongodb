Trabajo práctico 06- Refactorizacíon modular de reservas 


#Proyectos de partica y cambios 
este trabajo partde de la apliacion de reservas de salas de estudio desarrollado en el tp05, el objectivo fue reorganixar el codigo sin egregar funcionalidades nuevas ni modificar el funcionamiento de la apliacion.
Para eso, se separó el código que estaba en el src/index.js en distintos módulos, aplicando los principios de alta cohésion y baja acoplamiento, se distribuyeron las responsabilidades entre la configuracion, el arranque del servidor, las rutas, los controladores, los servidores y los middlewares.
También se incorporo ESLint y Prettier para revisar el código y amntener un formato consistente.



#Instalación y ejecución:
desde la carpte raíz del proyecto, instalar las dependencias: npm install

para iniciar el servidor con la configuracion predeterminada: npm start

también se puede ejecutar utilizando las variables de entorno  del archivo .env local: npm run start:local.
una vez iniciado el sercidor, ingresae desde el navegador: http://localhost:3000
para detenerlo, preciona Ctrl + C en la terminal 



#Configuración del entorno:

las configuracíon se centraliza en src/configuracion.js

PORT: define el puerto del servidorm si no se especifica, se utiliza el puerto 3000 se validad que sea número entero entre 1 y 65535.
NODE_ENV: determina el formato de los registros de Morgan, si el entorno es production, utiliza conbined; en los casos, utiliza dev.

el proyecto incluye un archivo .env.example como plantilla de configuración, el archivo .env local se mantiene excluido del repositorio mediante .gitignore, por lo que no se incluye datos de configuracion personales en esta entrega.



#Mapa de modulos y dependencias:
src/index.js: inicia la aplicación, carga los datos iniciales desde datos/salas.json, crea el servicio de reservas y levanta el servidor mediante app.listen().

src/configuracion.js: lee y valida las variables de entorno y configura el formato de Morgan.

src/app.js: configura Express, EJS, los archivos estáticos, los middlewares y el montaje de las rutas.

src/rutas/reservas.js: define las rutas de reservas y las conecta con los controladores y los middlewares correspondientes.

src/controladores/reservas.js: recibe las solicitudes HTTP, llama al servicio y prepara las respuestas para el cliente.

src/servicios/reservas.js: contiene la lógica de negocio y las operaciones para listar, buscar, contar y crear reservas.

src/middleware/solicitudes.js: genera identificadores BIB-XXXX y mide el tiempo de procesamiento de las solicitudes.

src/middleware/reservas.js: establece la sección activa de las vistas y valida los datos enviados desde el formulario.



#Pipeline y contrato de rutas

Las solicitudes pasan por los siguientes componentes, en este orden:

Morgan: registra las solicitudes recibidas.

Identificador de solicitud: genera un ID y lo guarda en res.locals.solicitudId.

Medición de duración: calcula el tiempo de procesamiento cuando termina la respuesta.

Archivos estáticos: permite acceder al CSS y otros recursos de public/.

Parsers: express.urlencoded() y express.json() procesan los datos recibidos.

Rutas principales: atienden la página de inicio y el estado de la aplicación.

Router de reservas: gestiona las operaciones relacionadas con las reservas.

Manejador de errores 404: responde a las rutas que no están definidas.



#Rutas de la aplicación

Método  Ruta           Función                                                                           Resultado esperado

GET     /              Muestra la página de inicio.                                                       200 OK

GET     /estado        Devuelve un JSON con la cantidad de reservas y el ID de solicitud.                  200 OK

GET    /reservas       Muestra el listado de reservas.                                                     200 OK

GET   /reservas/nueva  Muestra el formulario de creación.                                                   200 OK

GET  /reservas/:id     Muestra el detalle de una reserva.                                                  200 OK o 404 Not Found

POST /reservas          Valida y registra una reserva.                                                    302 Found o 400 Bad Request

Cualquier método      Ruta inexistente     Muestra la página de error.                                    404 Not Found

Las rutas de reservas se declaran con caminos relativos porque el router se monta en app.js bajo el prefijo /reservas. Por ejemplo, dentro del router se declara /:id, que al combinarse con el prefijo se convierte en /reservas/:id. Así se evita repetir el prefijo en cada ruta.

#Formato y análisis estático

Se incorporaron Prettier y ESLint como dependencias de desarrollo para mantener el formato del código y detectar posibles errores.

Los comandos utilizados y sus resultados registrados fueron:

npm run format:check: verifica el formato sin modificar los archivos. Resultado: todos los archivos cumplen con las reglas de formato.

npm run lint: analiza el código con ESLint. Resultado: 0 errores y 0 advertencias.

npm run check: ejecuta las comprobaciones de formato y análisis estático. Resultado: ejecución correcta, con código de salida 0.



#Persistencia temporal y límites

Las reservas se almacenan en un único arreglo en memoria, administrado por el servicio de src/servicios/reservas.js. Los datos iniciales se cargan desde datos/salas.json, pero las nuevas reservas se agregan al arreglo sin modificar ese archivo.

El servicio no utiliza res porque su función es trabajar con los datos y aplicar la lógica de negocio, no responder solicitudes HTTP. De esta manera, puede realizar sus operaciones sin depender directamente de Express.

El controlador, en cambio, recibe req y res, obtiene los datos enviados por el usuario, llama al servicio y decide cómo responder. Puede mostrar una vista, devolver un JSON, enviar un código de error o redirigir al usuario.

Como las reservas se guardan en memoria y no en una base de datos, los cambios no son permanentes. Cuando se detiene y se vuelve a iniciar el servidor, el arreglo se crea nuevamente y se cargan las reservas iniciales desde datos/salas.json. Por eso, las reservas creadas durante la ejecución anterior desaparecen.
